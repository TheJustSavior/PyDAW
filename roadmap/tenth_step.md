## 1. Пер-трековые scratch-буферы событий MIDI

**Файлы:** `engine/src/mixer.h`, `engine/src/mixer.cpp`,
`engine/src/vst_host.h`.

Раньше `mixMidiTrack()` каждый аудиоблок аллоцировал
`std::vector<VstHostEvent>` на стеке/куче. Теперь:

- структура `VstHostEvent` перенесена в `mixer.h` (Track может владеть
  буфером без зависимости от VST-заголовков);
- у каждой `Track` — поле `midiEvents`: `clear()` каждый блок сохраняет
  **ёмкость**, после прогрева аудиопоток **не делает heap-аллокаций**
  на VST-инструмент;
- `reserve(64)` выполняется один раз при первом использовании.

## 2. PDC с линиями задержки для live-входа

**Файлы:** `engine/src/mixer.{h,cpp}`, `engine/src/audio_engine.{h,cpp}`,
`engine/src/bindings.cpp`, `pydaw/engine_bridge.py`.

Добавлен второй режим компенсации задержки плагинов:

| `pdcMode` | Поведение |
|---|---|
| **0** (по умолчанию) | **Look-ahead** — дорожка рендерится на
`playhead + latency` (как в шаге 9). Нулевая добавленная латентность
мониторинга, идеально для таймлайна. |
| **1** | **Delay lines** — классическая схема: каждая дорожка
задерживается на `(maxPathLatency − ownPathLatency)` кадров кольцевым
буфером, все пути выравниваются по самой «медленной» цепочке. Подходит
для будущего live-мониторинга, где вход нельзя читать «вперёд». |

API:

- `engine.set_pdc_mode(0|1)` / `pdc_mode()`;
- `bridge.set_pdc_mode()` / `pdc_mode()` с фолбэком для старой сборки.

При нулевой латентности всех цепочек оба режима дают **бит-в-бит
идентичный** экспорт (проверено тестом).

## 3. Фоновая генерация пирамиды пиков при импорте

**Файлы:** `engine/src/audio_file.{h,cpp}`, `engine/src/audio_engine.cpp`.

Раньше базовая пирамида min/max (`kBasePeakSpp = 256`) строилась при
**первом** вызове `computePeaks()` — первая отрисовка волны большого
файла блокировала UI-поток на полное сканирование. Теперь:

- `AudioFile::buildPeaksAsync()` запускает `ensureBasePeaks()` в
  **отдельном потоке** сразу после декодирования;
- `AudioEngine::loadFile()` вызывает её автоматически при каждом
  импорте;
- `peaksMutex_` сериализует построение (фон + первый запрос UI);
- повторные сессии по-прежнему читают `*.peaks` с диска мгновенно.

## 4. Лимит размера дискового кэша (LRU)

**Файлы:** `engine/src/audio_cache.{h,cpp}`, `engine/src/audio_engine.cpp`,
`engine/src/audio_file.cpp`.

- Каталог кэша (`PYDAW_CACHE_DIR`, по умолчанию
  `%LOCALAPPDATA%/PyDAW/cache`) обходится **рекурсивно** — учитываются
  и подкаталоги Python (`stretch/`, `join/`).
- **LRU по mtime**: при чтении `.pcm` / `.peaks` файл «трогается»
  (`touchFile`), при записи получает свежий mtime.
- **`enforceLimit()`** удаляет самые старые файлы, пока суммарный размер
  не опустится ниже лимита; файлы, занятые mmap, пропускаются без ошибки.
- Лимит: **`PYDAW_CACHE_LIMIT_MB`** (по умолчанию **2048** МБ; `0` =
  без ограничения).
- **`enforceLimitAsync()`** вызывается при старте `AudioEngine` в фоне.

## 5. Параллельный рендер групповых шин

**Файлы:** `engine/src/mixer.{h,cpp}`.

Pass 2 микшера разбит на две фазы:

- **2a (параллельная).** Каждая групповая шина обрабатывает свой
  аккумулятор (FX, stereo width, gain/pan, пики) через `RenderPool`.
  Группы **не вкладываются** друг в друга — это один «топологический
  уровень» графа, все шины независимы.
- **2b (последовательная).** Готовые шины суммируются в мастер в
  исходном порядке дорожек — детерминированный выход.

На проекте «2 группы × 2 ребёнка + свободная дорожка» параллельный
рендер **бит-в-бит совпадает** с однопоточным (`PYDAW_MIX_THREADS=1`).

## 12. Фикс Ctrl+J для стыкующихся клипов

**Файлы:** `pydaw/ui/main_window.py`, `tests/test_gui_smoke.py`.

Проверка перекрытия перед склейкой (Ctrl+J) считала **любое**
`next.start < prev.end` наложением. При стыковке «вплотную» после
перетаскивания по сетке или конвертации beat↔frame второй клип часто
оказывается на **долю кадра раньше** конца первого — склейка
отклонялась, хотя на таймлайне зазора нет.

- Новый критерий `_join_clips_overlap`: реальное перекрытие только если
  `next.start + min_gap < prev.end`.
- **Аудио:** `min_gap = 1` кадр (стык `next.start == prev.end` и сдвиг
  на один sample допустимы).
- **MIDI:** `min_gap = 1 / frames_per_beat` (один кадр в битах).
- Частичное наложение по-прежнему блокируется; smoke-тест дополнен
  случаями «вплотную» и субкадровым slop.

## 14. Фикс зависания транспорта на ~00:00.145

**Симптом:** после нажатия Play звук пропадает, playhead и время
транспорта замирают (часто на **00:00.145** при 44.1 kHz — ~6394
кадров, т.е. через ~12–13 аудиоблоков).

**Причина (шаг 10):** параллельный рендер дорожек (`RenderPool`) +
офлайн-экспорт делят один глобальный пул и общие буферы `Mixer` без
сериализации. Возможные сценарии:

- поток экспорта вызывал `mixer_.mix()` пока realtime-callback ещё
  крутился внутри `RenderPool::run()` → порча `pending_` / job state,
  бесконечный spin-yield в audio thread, `exporting_` мог остаться
  поднятым → callback выдаёт тишину и **не двигает playhead**;
- worker-потоки рендера (pass 1a) вызывали
  `VstPlugin::setParamFromAudioThread()` с блокирующим `lock_guard` на
  `paramMutex`, который UI держит в `vst_sync_controllers()` → deadlock
  render pool ↔ UI;
- worker-потоки создавались **в первом audio callback** (`ensureStarted`)
  → xrun/останов драйвера на слабом буфере.

**Исправление:**

| Файл | Изменение |
|---|---|
| `engine/src/audio_engine.{h,cpp}` | `mixMutex_`: все обращения к
`mixer_` из callback и `exportWav()` сериализованы; `applyCommands()`
только под mutex; `ExportGuard` (RAII) гарантирует сброс
`exporting_`; `RenderPool::warmup()` при `start()`. |
| `engine/src/render_pool.{h,cpp}` | `runMutex_` на всё тело `run()`;
публичный `warmup()` для раннего старта workers. |
| `engine/src/vst_host.cpp` | `setParamFromAudioThread`: `try_lock`
вместо блокировки (пропуск одного блока автоматизации лучше deadlock). |
| `tests/test_step10.py` | `test_playback_advances`,
`test_playback_after_export`, `test_playback_during_export`. |

## 15. Фикс «дёрганья» playhead на ~00:00.145 (UI)

**Симптом (отдельно от §14):** движок идёт нормально, но при нажатии
Play линия playhead **прыгает вперёд** примерно на **00:00.145**
(~6394 кадров при 44.1 kHz) и затем возвращается — визуальный рывок.

**Причина:** `_smooth_playhead()` экстраполировал позицию по wall-clock
на 60 Hz, пока `playhead_frame` ещё 0 (первый audio callback в полёте).
За ~145 ms оценка убегала на ~12 буферов вперёд.

**Первый фикс (ошибочный):** потолок `raw + buffer` + часы транспорта
только по raw + сброс при Play. Побочный эффект: при редактировании
случайно удалена строка `self._timer = QTimer(self)` → `_on_tick` не
работал, playhead **застыл на 0**; отображение raw без сглаживания
тоже выглядело как «не движется».

**Итоговое исправление (`pydaw/ui/main_window.py`):**

- восстановлен `self._timer = QTimer(self)`;
- сглаживание: интерполяция по wall-clock с **потолком** `raw +
  buffer_frames` и **полом** `raw` (не убегать вперёд и не отставать);
- при seek/stop/rewind — сброс `_playhead_est`; при Play/Pause — нет
  лишнего сброса (состояние сбрасывается на первом paused-тике);
- транспорт и таймлайн используют одно сглаженное значение `frame`.

**Тест:** `test_playhead_smooth_cap` в `tests/test_step10.py`.

## 16. Финальный фикс playhead: `PlayheadSmoother`

**Симптом (после §15):** playhead «дёргается» около **00:00.011**
(~один буфер 512 кадров при 44.1 kHz) при старте воспроизведения.

**Причина:** сглаживание из §15 накапливало оценку `est += dt·sr`
независимо от движка и лишь потом зажимало её в коридор
`[raw, raw + buffer]`. UI-таймер (16 мс) и аудио-callback (~11.6 мс)
не синхронны, поэтому оценка постоянно билась то о потолок, то о пол
коридора — на экране это выглядело как дрожание на ширину буфера.
Проверено: сам движок playhead двигает корректно
(`test_playback_advances` и др. проходят) — проблема была только в UI.

**Исправление:** логика сглаживания вынесена в отдельный чистый модуль
`pydaw/ui/playhead_smoother.py` (класс `PlayheadSmoother`, без Qt —
юнит-тестируется напрямую):

- экстраполяция по wall-clock **заякорена на момент последнего
  изменения** значения движка (каждое обновление raw — новый якорь), а не
  накапливается от прошлой оценки — дрейф невозможен;
- потолок `raw + buffer_frames` — оценка не убегает вперёд
  (старый спринт до ~00:00.145);
- **монотонность** при обычном воспроизведении — линия не прыгает
  назад между тиками; seek назад и loop-wrap принимаются сразу
  (скачок > 0.25 с либо `raw + buffer < prev`);
- при остановке возвращается raw и состояние сбрасывается.

`MainWindow._smooth_playhead()` / `_reset_playhead_smooth()` теперь
делегируют смузеру; поля `_playhead_est*` и импорт `time` из
`main_window.py` удалены.

**Тест:** `test_playhead_smooth_cap` переписан на реальный
`PlayheadSmoother` (4 сценария: кап на старте, монотонность и
гладкость при идущем движке, seek назад, остановка).

## 17. Playhead неподвижен: недоступное сохранённое аудиоустройство

**Симптом:** playhead вообще не двигается (стоит на 00:00.000 или
дрожит в пределах одного буфера), звука нет.

**Диагностика:** временная трассировка `PYDAW_DEBUG_PLAYHEAD=1`
(строки `[playhead] raw=... playing=... running=...` в консоли,
~4 в секунду, `MainWindow._debug_playhead_tick`). В логе было видно:
`playing=True`, но `raw=0`, `audio_ok=False`, `running=False` —
аудиопоток вообще не открыт, callback не вызывается, движок не
продвигает playhead.

**Причина:** в настройках (`audio/*` в QSettings) сохранено ASIO
устройство (`device_id=132`, `api=asio`), которое при запуске
недоступно (занято другим приложением / отключено). `EngineBridge`
получал `False` от `engine.start(...)` и оставался без потока —
приложение «работало», но транспорт был мёртв.

**Исправление (`pydaw/engine_bridge.py`):** если старт с сохранёнными
устройством/API не удался, бридж повторяет `start()` с устройством по
умолчанию (`device_id=0`, `api=""`) и выставляет флаг
`used_fallback_device`. `MainWindow` показывает в статус-баре
«Saved audio device unavailable - using default output» (локализовано,
`pydaw/ui/i18n.py`). Проверено трассировкой: `running=True`,
`raw` растёт, playhead и звук работают.

## 18. ASIO пропал из списка устройств

**Симптом:** в Настройки → Аудио остался только WASAPI; ASIO-драйверы
исчезли (следствие §17: сохранённое ASIO-устройство и не могло
открыться — бэкенда больше не было в сборке).

**Причина:** установленный `pydaw_engine.pyd` был пересобран без ASIO.
Опция CMake `PYDAW_ASIO_SDK_DIR` по умолчанию пустая, и при обычной
пересборке (`cmake -S . -B ...` без флага) бэкенд `__WINDOWS_ASIO__`
молча выпадал, хотя ASIO SDK лежит в репозитории
(`engine/third_party/asio`).

**Исправление (`CMakeLists.txt`):** `PYDAW_ASIO_SDK_DIR` теперь по
умолчанию указывает на бандл-SDK
`${CMAKE_CURRENT_SOURCE_DIR}/engine/third_party/asio` — обычная
пересборка всегда включает ASIO (отключение: явно передать пустое
значение). Кэш сконфигурирован заново, движок пересобран, `.pyd`
установлен. Проверка:

```text
apis: [('asio', 'ASIO'), ('wasapi', 'WASAPI')]
asio devices: Ableton Move/Push, ASIO4ALL v2, FL Studio ASIO,
FlexASIO, Realtek ASIO
```

## 19. Файлы не открываются из папок с кириллицей

**Симптом:** при открытии проекта — «Некоторые аудиофайлы не найдены»,
хотя файлы на месте (`…\OneDrive\Документы\PyDAW\projects\MyProject\
samples\…`); терялись и склеенные (`a05077…wav`), и исходные сэмплы.

**Причина:** пути приходят из Python в движок как **UTF-8**
(pybind11), а `drwav_init_file` / `drflac_open_file…` /
`drmp3_open_file…` / `fopen_s` на Windows трактуют `char*` как **ANSI**
— любой путь с кириллицей («Документы») не открывался. Раньше это
маскировалось: файлы жили по ASCII-путям; папка
`Documents/PyDAW/projects` (§11) на русской Windows ввела кириллицу в
каждый путь проекта.

Примечание: предыдущая попытка фикса «сломала воспроизведение» не
из-за самого фикса — при той пересборке движок собрался **без ASIO**
(см. §18, пустой `PYDAW_ASIO_SDK_DIR`), сохранённое ASIO-устройство
перестало открываться (§17). Теперь ASIO включён по умолчанию, фикс
безопасен.

**Исправление (движок, UTF-8 → wide на Windows):**

- `engine/src/audio_file.cpp` — helper `widePath()` (`fs::u8path` →
  `wstring`); WAV: `drwav_init_file_w`; FLAC: `drflac_open_file_w` +
  `drflac_read_pcm_frames_f32`; MP3: `drmp3_init_file_w` +
  `drmp3_read_pcm_frames_f32`.
- `engine/src/audio_engine.cpp` — экспорт: `drwav_init_file_write_w`;
  удаление отменённого экспорта через `fs::remove(fs::u8path(...))`.
- `engine/src/audio_cache.cpp` — `writeFile()`: `_wfopen_s` вместо
  `fopen_s`, удаление tmp через `fs::remove`.

Проверено вживую: оба файла из «Документы» загружаются
(`load ok: (1, 1417844)`, `(2, 329142)`), ASIO в списке, playhead
двигается.

**Тест:** `test_unicode_path_load_and_export` в `tests/test_step10.py`
— загрузка WAV из папки «Документы юникод» + оффлайн-экспорт в неё же.

## 20. «Фейдер» на первой ноте MIDI-клипа (VST-инструмент)

**Симптом:** в ряду одинаковых MIDI-клипов первая нота очередного
клипа иногда вступает не сразу / плавно нарастает, как будто сработал
фейд; воспроизводится нестабильно (зависит от клипа).

**Причина (`engine/src/mixer.cpp`, `mixMidiTrack`, VST-путь):**

1. **NoteOff за границей блока.** Условие `noteEnd <= blockEnd`
   давало `sampleOffset == frames` — вне допустимого диапазона VST3
   `[0, frames)`. Часть плагинов такие события отбрасывает → нота
   «зависает» нажатой. Когда следующий клип берёт ту же ноту, синт
   не запускает огибающую заново, а крадёт голос с мягким ramp'ом /
   легато — слышно как «фейд» первой ноты. Проявляется только когда
   конец ноты попадает ровно на границу аудиоблока — отсюда
   нерегулярность.
2. **Порядок событий на одном кадре.** Когда клип A кончается той же
   нотой, какой начинается клип B (стык на одном кадре в одном блоке),
   порядок on/off в списке зависел от порядка клипов; NoteOn раньше
   NoteOff той же высоты убивает свежую ноту.

**Исправление:**

- `sampleOffset` NoteOff зажат в `min(noteEnd - playhead, frames - 1)`
  — событие всегда доставляется внутри блока;
- список событий сортируется по `(sampleOffset, NoteOff-раньше-NoteOn,
  pitch)` перед `processWithEvents` (in-place `std::sort`, без
  аллокаций на аудиопотоке).

## 21. Постоянный «фейд» нот на швах после склейки MIDI-клипов

**Симптом:** после Ctrl+J ряда MIDI-клипов «фейд» бывших первых нот
(§20) становится **постоянным** — на каждом шве склеенного клипа.

**Причина (`pydaw/engine_bridge.py`):** старт и длина ноты
конвертировались в кадры **независимо**:
`start = round(s·fpb)`, `length = round(L·fpb)`. Из-за раздельного
округления `round(s·fpb) + round(L·fpb)` может быть на **1 кадр
больше**, чем `round((s+L)·fpb)` — конец ноты «переползает» за начало
следующей ноты той же высоты. NoteOff первой ноты приходит **после**
NoteOn второй и глушит её голос (перекрытие, а не стык — сортировка из
§20 бессильна). В склеенном клипе ноты со швов получают такие
координаты всегда — эффект стал воспроизводимым на каждом шве.

**Исправление:** `_engine_note_span()` — конец ноты округляется на
битовой сетке тем же способом, что и старт следующей
(`end = beats_to_frames(start_beats + length_beats)`), длина =
`end − start`. Стыкующиеся ноты теперь кончаются ровно на кадре начала
следующей; порядок событий на одном кадре гарантирует §20
(NoteOff раньше NoteOn).

## 22. Щелчок на шве loop-региона

**Симптом:** при выходе петли на новый круг слышен щелчок — на аудио,
MIDI и смешанных проектах.

**Причина:** переход `loopEnd → loopStart` — жёсткий разрыв сигнала:
аудиоклипы обрываются на произвольной фазе волны, а MIDI-голоса
рвутся chase-ретриггером (нота перезапускается с атаки, встроенный
синт скачет по фазе). Никакого деклика на шве не было.

**Исправление (`engine/src/audio_engine.cpp`, loop-ветка
`process()`):** позиционный деклик-fade на мастере: затухание до нуля
на последних ~5 мс (`sampleRate/200` кадров) перед `loopEnd` и
нарастание с нуля на первых ~5 мс после `loopStart`,
**smoothstep**-кривая; для коротких петель длина ограничена половиной
петли. Рамп привязан к позиции таймлайна, поэтому работает и на
границе аудио-callback'а, и внутри блока (сегментный рендер).

Пробовался также вариант с кроссфейдом (рендер ~5 мс продолжения за
`loopEnd` и подмешивание в начало круга) — по результату прослушивания
откатен в пользу простого fade.

**Инструменты:** отладочная привязка `engine.debug_process(frames)`
(офлайн-прогон realtime-callback, только при незапущенном устройстве) +
численный пробник шва `tests/_tmp/seam_probe.py` (провал `|x|` до 0 на
шве и обратно — ожидаемое поведение fade).

## 23. Tweak: возврат контрола в дефолт после создания линии

**Файлы:** `pydaw/ui/main_window.py`.

Раньше после срабатывания Tweak (тронул крутилку/слайдер → диалог →
«Add lane») параметр оставался в том положении, куда его сдвинул
пользователь, и первая точка новой линии копировала это «случайное»
значение. Теперь жест Tweak — только выбор параметра:

- после закрытия диалога (и «Add lane», и **Cancel**) тронутый контрол
  **возвращается в дефолтное положение** (громкость → unity 1.0, панорама → центр,
  stereo width → 1.0, встроенный FX → дефолт из `EFFECT_DEFS`,
  VST/инструмент → `vst_get_param_default`); значение синхронизируется
  в модель, движок, шапку дорожки и микшер;
- **первая точка** линии автоматизации (`beat 0`) ставится в это же
  дефолтное значение, а не в текущее;
- незавершённый undo-жест крутилки сбрасывается
  (`_discard_param_gesture`) — движение, которым выбирали параметр,
  не попадает в историю undo.

Реализация: `_default_lane_value()` (нормализованный дефолт параметра),
`_reset_control_to_default()` (денормализация + существующие
`_apply_*`), у `_on_add_automation_lane()` появился необязательный
аргумент `initial` (все прочие пути создания линий по-прежнему берут
текущее значение через `_initial_lane_value`).

## 24. Автоматизация: редактирование только развёрнутой полосы

**Файлы:** `pydaw/ui/timeline.py`, `pydaw/ui/automation_item.py`.

- Точки автоматизации теперь редактируются **только у развёрнутой
  (выбранной) полосы**. Компактная полоса (44 px) и свёрнутые lanes
  (`▸A`) — read-only: клики/перетаскивания игнорируются, случайно
  сдвинуть точку на узкой полосе нельзя. Развернуть полосу — кликом
  по её заголовку в панели дорожек (повторный клик сворачивает);
  созданная через Tweak/меню линия выбирается автоматически и сразу
  доступна для редактирования.
- `TimelineView.is_automation_editable()` получил необязательный
  `lane_id`: с ним проверяется и выбор конкретной полосы
  (`_selected_lane`), без него — прежняя проверка только fold-состояния.
- Кривая развёрнутой полосы рисуется **толще** (2.5 px вместо 1.5 px) —
  её лучше видно и проще попадать по сегментам.
- Компактная (не выбранная) полоса рисуется **нейтральным серым из
  темы** (`TEXT_FAINT` — линия и заливка точек, `BORDER_SOFT` — обводка
  точек) вместо акцентного цвета: по цвету сразу видно, что полоса
  read-only. Развёрнутая полоса — акцентный цвет, как раньше.

## 25. Импорт аудио — всегда новая дорожка в конце

**Файлы:** `pydaw/ui/main_window.py`.

`File → Import audio file…` раньше клал файлы на **первую существующую
аудиодорожку** (и мог смешать импорт с уже лежащими там клипами).
Теперь при каждом импорте создаётся **новая аудиодорожка в конце
списка** (перед мастером, `add_track(anchored=False)`), и все выбранные
файлы добавляются на неё. Создание дорожки и добавление клипов —
отдельные undo-шаги, как и раньше.

Клипы при импорте **не накладываются**: запрос идёт с `frame = -1`
(«добавить в конец дорожки»), а фактическая позиция вычисляется в
`_on_file_loaded` в момент готовности файла — после конца последнего
клипа, уже лежащего на дорожке. Файлы декодируются асинхронно, поэтому
расчёт «на приёме» гарантирует отсутствие наложений при любом порядке
завершения загрузок.

## 26. Шорткаты с буквами не работали в русской раскладке

**Файлы:** `pydaw/ui/keys.py` (новый), `pydaw/ui/timeline.py`,
`pydaw/ui/main_window.py`, `pydaw/ui/piano_roll.py`.

**Симптом:** Ctrl+J (и другие буквенные шорткаты, обрабатываемые через
`keyPressEvent`: Ctrl+C/V/D/A/R, F, Q) периодически «не срабатывали».
Логика склейки была цела (проверено скриптом-репро: два смежных
MIDI-клипа склеиваются). Причина — **раскладка клавиатуры**:
`QKeyEvent.key()` для буквенных клавиш отражает активную раскладку, в
русской физическая клавиша J даёт код кириллической буквы «О», и
сравнение `key == Qt.Key_J` молча не проходит.

**Исправление:** модуль `pydaw/ui/keys.py`, функция `letter_key(event)`
— возвращает layout-независимый код буквы через
`event.nativeVirtualKey()` (Windows VK-коды `0x41..0x5A` и X11-keysym
латиницы совпадают с ASCII), для остальных клавиш — обычный
`event.key()`. Подключена во всех трёх `keyPressEvent`
(таймлайн, главное окно, piano roll). Меню-шорткаты (`QAction`) Qt
обрабатывает layout-независимо сам — их не трогали.
